## What Is WizardCD?

WizardCD is a **self-hosted Java application deployment framework** built by EBB Systems.
It deploys Spring Boot (and other Java) applications to Linux VMs via SSH — no Docker, no Kubernetes, no CI/CD pipelines required.

- Self-hosted, network-contained (not SaaS)
- Multi-environment: **SIT / UAT / PROD**
- VM-based SSH deployments — Tanuki Service Wrapper for process lifecycle
- Per-environment ED25519 SSH key isolation (keys auto-generated by the runner)
- Real-time job tracking, log streaming, and abort control
- Backup-before-deploy with configurable retention (1–5 releases)
- Tagline: **"One Config. One Command. Continuous Magic."**

## Job Lifecycle (State Machine)

```
CREATED → VALIDATING → PREPARING_WORKSPACE → RUNNING → SUCCESS
                                                     └→ FAILED
                                                     └→ ABORT_REQUESTED → ABORTED
```

**Exit code interpretation (RunnerServiceImpl):**
| Exit code | Meaning |
|-----------|---------|
| `0` | SUCCESS |
| `-1` | FAILED (runner-enforced timeout) |
| `-2` | ABORTED (runner-enforced abort) |
| Any positive | FAILED (deploy.sh shell error) |

**deploy.sh exit codes (contract with runner):**
| Code | Constant | Meaning |
|------|----------|---------|
| 10 | EXIT_INVALID_ARGS | Bad arguments |
| 11 | EXIT_YAML_INVALID | YAML parse/validation error |
| 12 | EXIT_ARTIFACT_MISSING | JAR or lib dir missing |
| 20 | EXIT_WRAPPER_FAILED | Tanuki config generation failed |
| 30 | EXIT_PACKAGE_FAILED | Tarball packaging failed |
| 40 | EXIT_SCP_FAILED | SCP transfer failed |
| 50 | EXIT_SSH_FAILED | (reserved) |
| 60 | EXIT_REMOTE_FAILED | application-deployment.sh failed |

## Full End-to-End Deployment Flow

### Phase 1 — Java (runner-service-ms)

1. `POST /jobs` → `RunnerController.submit()` — validates, generates UUID jobId, returns 202 immediately
2. `RunnerServiceImpl.runDeploy()`:
   - State machine: `CREATED → VALIDATING → PREPARING_WORKSPACE`
   - `DeploymentValidatorService.validate(request)`
   - Submits `executeJob()` to single-thread executor (serialized deployments)
3. `RunnerWorkspaceServiceImpl.prepareWorkspace()`:
   - Creates `workspace/jobs/<jobId>/input|build|logs|wrappers/`
   - Saves JAR → `INPUT_DIR/<effectiveJarName>`
   - Extracts libZip → `INPUT_DIR/lib/` (JARs at root — see ZIP rule below)
   - Extracts certZips → `INPUT_DIR/<certPaths[i].source>/` (by index)
   - Extracts extraZips → `INPUT_DIR/<extraDirs[i].dirName>/` (by index)
   - **ZIP-slip protection**: rejects any entry whose path escapes targetDir
4. `YamlGenerationServiceImpl.generateYaml()` → writes `INPUT_DIR/deployment-config.yml`
5. `SshKeyServiceImpl.getPrivateKeyPath(env)` → resolves private key path (auto-generates if missing)
6. State: `RUNNING` → launches `./deploy.sh --job-id <id> --config <yaml-path>`

### Phase 2 — Bash (deploy.sh on runner VM)

1. Parse args `--job-id` + `--config`; set up job workspace dirs
2. Source `helpers.sh` (logging)
3. Run `ensure_yq_installed()` — enforces yq v4.44.3 (auto-installs if wrong version)
4. Parse YAML with yq → set all variables (APP_NAME, ENV_NAME, SSH_*, JAVA_*, etc.)
5. Validate local artifacts (`FULL_JAR`, `FULL_LIB`)
6. Run `generate-tanuki-wrapper-conf.sh --app --env` → generates `<app>-<env>.conf` + `<app>-wrapper.sh`
7. Stage artifacts → `BUILD_DIR/stage/bin|conf|lib/`
8. `tar -czf TARBALL BUILD_DIR/stage/`
9. `scp TARBALL → /tmp/<app>-<env>.tar.gz` on target
10. If `cert_paths` → loop: `ssh mkdir -p <targetPath>` + `scp <CERT_LOCAL>/. → <targetPath>/`
11. If `extra_dirs` → loop: `ssh mkdir -p <target_path>` + `scp <EXTRA_LOCAL>/. → <target_path>/`
12. `ssh "bash -s" < application-deployment.sh <APP> <ENV> <HOST> <BASE_PATH> <PORT> <JAVA_VER> <USER> <BACKUP> <MAX_BACKUPS> <STABILITY_WINDOW>`

### Phase 3 — Bash (application-deployment.sh on target VM)

1. Stop running app: `<app>-wrapper.sh stop` → fallback: kill by port
2. Create dirs: `logs/`, `backup/`
3. Extract tarball → `DROP_DIR`
4. `create_release_backup()` → backup `bin/ + conf/ + lib/` into `backup/releases/<timestamp>.tar.gz`
5. `deploy_directory` for `bin/`, `conf/`, `lib/`
6. Deploy any extra dirs from DROP_DIR (beyond bin/conf/lib)
7. `start_app()` → run `<app>-wrapper.sh start`
8. **Stabilization phase** (configurable 5–120s, default 20s): check wrapper status=STARTED, PID file exists, process alive, port bound — progress logged as "Monitoring: Xs/Ys (Z%)"
9. Clean up DROP_DIR + stale tarballs in /tmp

## Tanuki Service Wrapper Details

`generate-tanuki-wrapper-conf.sh` reads the YAML and uses `sed` to fill templates:

| Template variable | Source |
|-------------------|--------|
| `{{APP_NAME}}` | appName |
| `{{APP_HOME}}` | deployment.target.base_path |
| `{{JAVA_CMD}}` | java.command |
| `{{APP_JAR}}` | app.jar_name |
| `{{MAIN_CLASS}}` | app.main_class (or `org.springframework.boot.loader.launch.JarLauncher` for fat JAR) |
| `{{JVM_XMS/XMX/NEW_RATIO}}` | jvm.* |
| `{{LOGFILE_MAXSIZE/MAXFILES}}` | logging.* |

**Deployment mode detection:**
- `lib_path == ""` or `null` → **FAT_JAR** → `MAIN_CLASS` overridden to Spring Boot JarLauncher
- `lib_path == "lib"` → **EXTERNAL_LIB (Thin JAR)** → uses app's own `MAIN_CLASS`

## SSH Key Service (SshKeyServiceImpl)

- Keys auto-generated with `ssh-keygen -t ed25519` on first access (synchronized)
- Stored at `~/.ssh/wizardcd_<env>_ed25519` (lowercase env name)
- Private key path **never supplied by client** — resolved server-side from `environment` field (prevents path traversal)

- `testConnection()` runs `ssh -o BatchMode=yes -o StrictHostKeyChecking=accept-new ... echo ok`; on success runs a second SSH to `find /usr/lib/jvm /usr/local/lib/jvm /opt/java /opt/jdk -name 'java' -type f` and returns `javaInstallations: List<String>` in `SshTestResult`

## deploy.sh — Critical Details

```bash
# Invocation signature:
./deploy.sh --job-id <uuid> --config <absolute-path-to-yaml>

# Key variables set from YAML:
APP_NAME, ENV_NAME, SSH_USER, SSH_HOST, SSH_PORT, SSH_KEY

```

**lib/ ZIP packaging rule (CRITICAL):**
```bash
# ✅ Correct — JARs at root of ZIP (deploy.sh does: cp -r "$FULL_LIB/"* ):
cd lib && zip ../lib-deps.zip *.jar

# ❌ Wrong — creates lib/lib/*.jar on server:
zip -r lib-deps.zip lib/
```

**yq enforcement:** deploy.sh auto-installs yq v4.44.3 if missing or wrong version.
Uses `curl` to download from GitHub releases. Requires sudo or root.

**Logging** (all to deploy.log via helpers.sh):
```bash

log_warn "message"           # [WARN ] [job=<id>] message
log_error "message"          # [ERROR] [job=<id> line=N] message → stderr
```

**SSH/SCP conventions:**

## Lib ZIP Packaging Rule (CRITICAL — re-documented)

The Tanuki conf template expects dependency JARs at `%MYAPP_HOME%/bin/lib/*.jar`.
deploy.sh stages them there. If the lib ZIP has a nested `lib/` folder inside it, `find` flattens them:

```bash
# ✅ Correct — JARs at root of ZIP:
cd lib && zip ../lib-deps.zip *.jar

# ⚠️  Also OK now — deploy.sh uses `find` to flatten:
zip -r lib-deps.zip lib/    # creates lib/lib/*.jar in workspace, but find still finds them
```

## Re-deploy Flow — Architecture

### How it works
1. Every successful deploy saves `request.json` in `workspace/jobs/<jobId>/input/`
2. `POST /jobs/:id/redeploy` loads the original config, accepts new JAR/lib/certs/extras
3. Creates a new job with `jobType="redeploy"`, reusing all config from the original
4. Standard deploy pipeline runs with the new artifacts

### RedeployModal.tsx
- Triggered from Dashboard table rows and JobDetailPage header (successful jobs only)
- JAR upload with drag-drop; detects fat/thin via `detectJarType()`
- Conditional lib ZIP upload when thin JAR detected
- Per-file upload progress bars
- Shows source job reference

### RollbackModal.tsx
- Triggered from Dashboard table rows and JobDetailPage header
- Pre-loads backup info via `GET /jobs/:id/rollback/preflight`
- Shows: backup date, size, target host
- PROD-specific warning banner
- "What happens" — 3-step rollback sequence
