Platform Overview

What is WizardCD?

WizardCD is a self-hosted Java application deployment framework built for engineering teams who need production-grade deployments without the overhead of containerisation platforms, managed CI/CD pipelines, or cloud-native complexity. It runs on your own infrastructure, connects directly to your VMs over SSH, and manages the full deployment lifecycle from JAR upload through to process stabilisation — with real-time visibility at every step.

"WizardCD is not a SaaS. It is installed on your own infrastructure — your network, your keys, your control."

Self-Hosted
Runs on your own runner VM. No external SaaS dependencies. No data leaves your network.
SSH-Based Deployments
Connects to target VMs over ED25519 SSH. No agents required on the target.
No Docker or Kubernetes
Deploys directly to the host OS. Works on any Linux VM — bare metal, EC2, or on-premise.
Multi-Environment
SIT, UAT, and PROD environments with isolated SSH keys and independent configurations.
Tanuki Process Manager
Manages application lifecycle via Java Service Wrapper — reliable start, stop, and restart.
Real-Time Job Tracking
Live log streaming, deployment phase indicators, and abort control during any job.
Backup Before Deploy
Captures a versioned backup of the running application before every deployment.
One-Click Rollback
Restore the previous release from backup with a single action in the dashboard.
Key Capabilities at a Glance
  • 4-step guided deployment wizard — no manual scripting required
  • Automatic JVM and Tanuki wrapper configuration generation
  • Fat JAR and thin JAR support with automatic detection
  • Per-environment SSH key auto-generation and management
  • Configurable deployment stability window (5–120 seconds)
  • Structured deployment log viewer with phase navigation
  • Re-deploy flow — reuse stored config, supply new JAR only
  • Pre-flight connectivity and permission checks before deploy

Deployment Phases
Phase 1 — Runner Service (Java)
Validates the deployment request, prepares the job workspace, extracts uploaded artifacts, generates the deployment YAML, resolves the SSH private key, and launches the deployment script.
Phase 2 — Deploy Script (Bash)
Parses YAML with yq, stages all artifacts, generates the Tanuki wrapper configuration, packages a tarball, transfers it via SCP, then streams application-deployment.sh to the target via SSH.
Phase 3 — Remote Deployment (Target VM)
Stops the running application, creates a versioned backup, extracts and deploys the new artifacts, starts the process via Tanuki wrapper, and monitors stabilisation over a configurable window (5–120 seconds).

Feature Set

Core Capabilities

01 / WIZARD
Deploy Wizard
A guided 4-step deployment form walks engineers through every configuration decision — from SSH target and Java binary selection to JVM tuning and backup policy. Auto-detects JAR type, reads manifest metadata, and validates connectivity before any deployment runs.
4-step wizard JAR auto-detection manifest parsing pre-flight validation
02 / MONITORING
Real-Time Job Tracking
Every deployment is a live job with streaming log output, structured phase indicators, and full state history. Engineers can drill into any deployment phase, focus on a single step's log output, or switch to raw view — all while the job is still running.
live log streaming phase navigation abort control state history
03 / RESILIENCE
Backup & Rollback
Before every deployment, WizardCD captures a versioned backup of the running application (binaries, config, libraries). If a deployment fails or introduces a regression, a single rollback action restores the previous release — no manual file management required.
pre-deploy backup configurable retention one-click rollback backup preflight
04 / SECURITY
SSH Key Management
WizardCD auto-generates a unique ED25519 SSH keypair for each environment (DEV, SIT, UAT, PROD) on first use. Private keys are stored server-side and never exposed to the client. Engineers copy only the public key to their target VMs — reducing credential surface to a minimum.
ED25519 keys per-environment isolation auto-generated server-side private key
05 / ENVIRONMENTS
Multi-Environment Support
DEV, SIT, UAT, and PROD environments are first-class citizens. Each environment has its own SSH key, independent configuration, and separate job history. Colour-coded throughout the UI — impossible to confuse a PROD deployment with a SIT test.
DEV / SIT / UAT / PROD isolated configurations colour-coded UI independent job history
06 / JVM
JVM Configuration
A dedicated JVM configuration panel lets engineers select a garbage collector (G1GC, ZGC, Shenandoah, or ParallelGC), set heap bounds, enable container-aware resource detection, and choose a workload profile. All flags are generated automatically with version-aware validation.
GC selector heap configuration container-aware workload profiles
Additional Capabilities
Re-Deploy Flow
Reuse the stored configuration from any successful deployment. Supply only the new JAR — all settings are preserved automatically.
Certificate & File Deployment
Upload TLS certificates and additional configuration directories alongside each deployment. Deployed to configurable target paths.
Notification System
In-app notifications alert engineers when any deployment, re-deploy, or rollback completes — with direct navigation to the job detail.

Key Isolation Principle
Each environment has its own ED25519 SSH keypair, auto-generated by the runner service on first access. The private key is stored exclusively on the runner VM and is never transmitted to the client browser. Engineers add only the public key to each target VM's authorized_keys.
Configuration Independence
SIT, UAT, and PROD configurations are entirely independent. A deployment to SIT does not share SSH credentials, target hosts, or deployment paths with UAT or PROD. Each environment maintains its own job history, backup set, and deployment log archive.

Get Started

Deploy Your First Application

WizardCD is ready to run on a single Linux VM.
No cloud accounts, no container registries, no pipelines to configure.

1
Install the Runner Service
Deploy runner-service-ms.jar to a Linux VM. Configure it as a systemd service. The runner generates its own SSH keys on first start and exposes the REST API on port 8081.
2
Configure SSH Access
Open the WizardCD UI and navigate to the Keys panel. Copy the generated public key for your target environment and add it to the ~/.ssh/authorized_keys file on each target VM. Run the connection test to verify.
3
Deploy Your First Application
Click New Deploy in the sidebar. Complete the 4-step wizard — select your environment, upload your JAR, configure the JVM, and review. Hit Deploy and watch the live log stream. Your application is running.
